# Generation attempt lifecycle (SCRUM-65 increment 2)

An attempt ID binds one immutable request fingerprint. The public generation endpoint rejects missing specifications, unsupported generation types, and unsupported packaged fragment versions before reservation. Once a page, selected metadata version and authenticated user resolve, internal packaged-input preparation failures reserve an attempt and persist `CONFIG/CONFIG_MISSING`. Fingerprint preparation uses one length-framed path; unavailable packaged resources contribute a stable sentinel and produce the same recorded configuration failure. `GenerationWorkflow` reserves and commits an `IN_PROGRESS` run before calling the generation engine. Contract validation inside generation is recorded as `CONTRACT/VALIDATION_FAILED`. A completed result is validated and stored against that same run, retaining the existing `SUCCESS`/`BUILD_FAILED` responses and artifact history. Other failures before a complete result persist `FAILED`, a fixed `failure_stage` (`CONFIG`, `CONTRACT`, `AI`, `ASSEMBLY`, or `FINAL_VALIDATION`) and a bounded code. Exception text, provider output, credentials, prompts and partial artifacts are never stored in those fields. No failed or interrupted attempt is registered as a runnable export.

An API failure retains the five-field `ApiResponse` envelope, with `body: null` and `errors` containing only field or `_global` messages. A persisted `FAILED` attempt owned by the authenticated requester supplies `X-Generation-Run-Id`, `X-Generation-Failure-Stage`, and `X-Generation-Failure-Code` response headers. The values come from the saved run and fixed stage/code enums, never exception text. Missing, incomplete, differently owned, or unreadable attempts yield the original safe error response without these headers. No headers are added to authorization failures. Existing successful generation and run-detail responses remain unchanged. The separate failure-detail endpoint remains unavailable pending SCRUM-61 integration below.

Reusing an attempt ID with changed inputs is rejected by its fingerprint. Reusing a successful or build-failed ID returns its recorded result; the provider does not run again. Reusing an `IN_PROGRESS`, `FAILED`, or `INTERRUPTED` ID reports the saved status and does not restart work. A fresh attempt after failure needs a new ID and a new fingerprinted run. Concurrent requests for the same ID are constrained by the unique database key; only the reserving request may proceed.

If the process stops after reservation, its row remains `IN_PROGRESS` so it cannot be mistaken for success. No automatic or callable status reset is provided in this increment: without a durable worker-ownership check, changing an `IN_PROGRESS` row to `INTERRUPTED` could overwrite an active worker. After confirming the original process is stopped, an operator may start a fresh attempt ID; the abandoned row remains visible for later controlled reconciliation. A future recovery operation must prove the worker no longer owns the attempt before marking it `INTERRUPTED`. No age-based reset is performed.

`sql/V8__add_generation_attempt_lifecycle.sql` adds nullable failure columns and extends the status check without rewriting prior rows. Current `develop` ends at V6, while the pending SCRUM-61 recovery reserves V7 for `bootstrap_entity_permissions`; apply V8 after that V7 at integration. H2 tests apply V8 after the current V6 baseline; production schema remains under explicit SQL migration control. The migration is additive and does not reset GSUIF data. Do not renumber or reapply a migration already recorded in a shared database.

## Diagnostic access review gate

`GET /api/v1/generation/runs/{id}/failure` is currently fail-closed with 403, including for the triggering user. SCRUM-61's `EntityPermissionChecker` is absent from this worktree. Before enabling details, integrate that existing checker and require both `ENTITY_ACCESS:GsuifPage` and `ENTITY_ACCESS:MetadataVersion` in the service, in addition to run ownership. The checker resolves grants from the user's roles and persisted permission codes; JWT authority strings alone are not sufficient. Add a positive integration test for an owner with both persisted grants and negative tests for either missing grant, another user and anonymous access. Until then, no caller can retrieve failure details through this endpoint.

The approved header design is documented on the generation operation's 400 and 500 OpenAPI responses. This backend has no configured CORS origin policy, so no CORS setting was changed. If a cross-origin frontend is deployed, its selected gateway/backend CORS policy must expose exactly these three headers to permitted origins; allowed origins must be reviewed separately and must not be broadened by this increment.

Later assembly increment requirements: create build inputs from the selected versioned descriptors, not fixed AssetTicket fixtures; record the actual provider identity and version; keep long provider/build operations outside database transactions where practical while retaining atomic result/artifact registration; and demonstrate an exported application for another domain without unintended AssetTicket names, files or dependencies. None of these assembly changes is implemented in this increment.
