# Initial complete-output persistence mapping gate

For BACKEND and FULL_STACK complete-output descriptors, `BigDecimal` is unsupported until the generation specification can provide explicit precision and scale. Preflight rejects it before a descriptor or rendered files exist. This limit does not change the legacy fragment path or the shared entity template's legacy `BigDecimal` rendering.

Complete-output enum entity fields retain `@Enumerated(STRING)` and explicitly use `@JdbcTypeCode(SqlTypes.VARCHAR)`. Their selected contract values must be Java enum identifiers and fit the field's explicit `columnLength`, or 255 when no length is set. This is checked before definition rendering. The shared `entity.ftl` enables the Hibernate annotation only when the complete-output renderer supplies `explicitVarcharEnumMapping=true`; absent/false preserves the legacy template default. Non-enum scalar fields do not receive the annotation. The public legacy context builder continues to reject explicit enum column lengths; only complete-output BACKEND/FULL_STACK can use them.

The focused test compiles an emitted entity and inspects Hibernate ORM 7.2.24.Final metadata using PostgreSQL dialect with JDBC metadata access disabled. It confirms the enum property's JDBC type is `VARCHAR` without a database connection. No migration or PostgreSQL `CHECK` constraint is emitted by this gate. A future migration renderer must derive and test the database constraint from the same selected contract values.

This partial generated output remains non-runnable. Account authentication/bootstrap, full-package assembly, and repeated application startup remain later review steps. Username normalization remains an unapproved proposal pending account/security review.

The internal projection derives the entity table directly from a frozen BACKEND/FULL_STACK descriptor. It contains a UUID primary key; every supported field in column-name order; non-null inherited `created_at`, `updated_at`, `created_by`, and `last_modified_by`; and exact enum `CHECK` values from the selected create, update, and response schemas. Its scoped SQL template produces an in-memory fragment consumed directly by V1. PostgreSQL names must be unquoted lowercase identifiers of at most 63 UTF-8 bytes; support-column, reserved-word, duplicate-column, and generated-constraint-name collisions fail before template output.

The persistence profile reserves `user_accounts`, `user_account_roles`, and `app_revision` for app-owned support tables, plus Flyway's `flyway_schema_history`. Entity table names cannot use them. Audited descriptors also project the derived `<entity_table>_aud` name and validate its identifier length and namespace before SQL rendering.

V1 now consumes that immutable entity projection directly and adds app-owned account/role tables. `username` is `varchar(100) NOT NULL UNIQUE` with PostgreSQL's initial case-sensitive storage (`Alice` and `alice` are distinct); there is no lowercase/ASCII normalization or normalization `CHECK`. Authentication matching policy remains for security review. `password_hash` is required but no account, default password or bootstrap data is seeded. The `ROLE_ADMIN`/`ROLE_USER` element collection uses LAZY loading; the later authentication service must load roles within its transaction. The role FK uses `ON DELETE RESTRICT`, without implicit cascade.

The earlier Envers revision-key proposal used `integer`. V1 deliberately uses Java `Long` and PostgreSQL `bigint GENERATED BY DEFAULT AS IDENTITY` for the revision key, giving the revision history a wider range without changing its strategy. The audited table's `rev` FK is also `bigint`. With pinned Hibernate Envers 7.2.24.Final, the generated `@RevisionTimestamp long` maps to `revtstmp bigint` epoch milliseconds. The complete-output entity opts into auditing all inherited audit-base properties; the shared legacy template default stays unchanged. Audited V1 uses the projected table name, field types and exact enum values, a `(id,rev)` primary key, a restrictive FK to `app_revision`, and nullable copied fields for delete revisions. The isolated PostgreSQL test verifies Flyway migration and repeat initialization, Hibernate schema validation, emitted JPA persistence, revision timestamp/type, inherited audit values, delete-row nullability, constraints, and a deliberate validation failure. The generated application still lacks later security/bootstrap and assembly files and is not yet runnable.
